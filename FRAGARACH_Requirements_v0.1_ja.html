1. 文書の目的

本書は、仮称 Knowledge Refiner として検討してきたOSS製品を、FRAGARACHとして実現するための要件を定義する。対象は、フォルダまたはファイル一覧として与えられる玉石混交の資料群を、利用目的に沿って分析し、根拠を保持した整合的な知識成果物へ変換するツールである。

本書では、製品の責務境界、入力・中間表現・出力、増分再コンパイル、LLMとSkillの役割、Rust／npmを中心とした実装方針、MVPの受入基準を定める。

本書の要点

FRAGARACHはRAG基盤ではない。RAGやAgentが利用する前段で、何を知識として構造化し、何を整合性として検査し、何を検索・回答・評価条件とするかをコンパイルする。

2. 背景と課題

2.1 背景

  • 企業内の大量文書は、重複、版違い、旧資料、未承認資料、表記揺れ、矛盾、適用範囲不明、所有者不明を含むことが多い。

  • 一般的なRAGは文書を直接チャンク化して索引へ投入するため、入力コーパスの品質と構造が回答精度の上限になる。

  • 企業RAGは多くの場合、Onboarding、規程照会、レビュー支援、障害対応など利用目的が先に定まっている。

  • 利用目的が分かれば、必要なエンティティ、関係、完全性条件、整合性条件、検索単位、回答要件を仮説化できる。

2.2 現在の空白

項目 内容
文書解析 PDF・Office文書をMarkdownや構造化文書へ変換するOSSは存在する。
社内検索・RAG 取得、索引、検索、チャットを提供する製品は多数存在する。
Knowledge Graph エンティティ・関係抽出やグラフ構築の研究・ツールは存在する。
不足する工程 利用目的と資料群を同時に入力し、ドメインモデル、整合性条件、根拠付き知識、検索仕様、評価仕様まで一つの再コンパイル可能な成果物として生成する定番OSSが弱い。

3. 製品コンセプトと独自ポジション

3.1 製品ビジョン

FRAGARACH — 問いに答え、真実を露出させる刃

FRAGARACHは、雑多な資料群を一律に検索可能にするのではなく、利用目的を刃筋として、必要な対象・関係・規則・例外・根拠を切り分ける。矛盾や不足を無理に隠さず露出させ、問いに答えられる知識体系を生成する。

図1　FRAGARACHの製品ポジション

3.2 独自ポジション

項目 内容
FRAGARACHが担う 利用目的の定義支援、想定エンティティ・関係の提案、根拠付き抽出、名寄せ、版・矛盾・不足の診断、目的別Knowledge Build、検索・回答・評価仕様の生成。
FRAGARACHが担わない 本番ベクトルDB、検索API、チャットUI、全社権限管理、継続的なKnowledge Management運用。
下流との関係 RAG、Agent、Wiki、検索基盤は交換可能なExporter／出力先として扱う。

3.3 設計原則

  • Purpose-first: 資料を読む前に、何に使い、何を理解・判断したいかを得る。

  • Evidence-preserving: すべての抽出知識から原文・ページ・節・セル等へ遡れる。

  • Hypothesis-driven schema: 利用目的からドメインモデルを仮説化し、資料によって検証・拡張する。

  • Consistency is purpose-dependent: 整合性を単なる文一致ではなく、用途に必要な判断を一貫して行える状態として定義する。

  • Incremental compilation: データ、利用目的、ドメインモデルの増減に応じて影響範囲だけ再処理する。

  • Downstream-neutral: 特定のRAG、Vector Store、Graph DBへ依存しない。

  • Human-confirmable: 自動的に真実を確定せず、候補、根拠、警告、未解決事項を提示する。

  • Local-first: 企業文書を扱うため、標準はローカル実行とし、外部送信を明示的に制御する。

4. 目標と非目標

4.1 目標

  • フォルダまたはファイル一覧から文書台帳と再現可能なSource Manifestを生成する。

  • 利用目的から、想定エンティティ、関係、イベント、属性、整合性条件をLLMで提案する。

  • 資料群から根拠付きの実体、関係、Claim、規則、手順、例外を抽出する。

  • 重複、名寄せ、版違い、時間的矛盾、権威性の競合、欠落を診断する。

  • 同一資料群から複数の利用目的別Knowledge Buildを生成する。

  • データ・目的・スキーマ変更時に影響範囲だけ再コンパイルする。

  • 下流RAG向けに検索仕様、回答契約、評価セットを出力する。

  • Rust製CLIをnpmから一行で導入できる。

4.2 非目標

  • 汎用チャットUIや本番社内検索サービスを提供すること。

  • Vector StoreやKnowledge Graph DBを独自実装・運用すること。

  • 企業内のアクセス権を下流検索基盤まで一貫して管理すること。

  • 入力資料から唯一の「真実」を完全自動で確定すること。

  • あらゆる業界に通用する巨大な万能オントロジーを事前定義すること。

  • 複雑PDF・OCR・表解析をRustだけで完全再実装すること。

  • MVPでSharePoint、Webクローラ、常時同期を完成させること。

5. 想定利用者とユースケース

5.1 想定利用者

項目 内容
RAG／Agent開発者 資料投入前に知識構造、検索単位、評価仕様を構築したい。
ドメイン専門家 資料間の矛盾や不足を確認し、何が正式な知識か判断したい。
Onboarding担当 大量資料から新任者が業務を遂行できるKnowledge Packを作りたい。
品質・監査担当 規則、例外、責任者、証跡、有効期間を一貫して確認したい。
OSS開発者 目的・分野別Skill、Parser、Exporterを追加したい。

5.2 代表ユースケース

ユースケース 目的
UC-01 Onboarding 部署資料から役割、業務フロー、成果物、利用システム、参照規程、問い合わせ先を抽出する。
UC-02 レビュー支援 成果物のレビュー要否、承認条件、指摘分類、例外条件、根拠規程を知識化する。
UC-03 規程・監査 義務、統制、証跡、責任者、例外、有効期間を抽出し、矛盾や参照切れを検出する。
UC-04 業務引き継ぎ タスク、担当者、依存、意思決定、未解決事項、期限、成果物、リスクを整理する。
UC-05 障害対応 症状、原因、切り分け、処置、停止条件、エスカレーション先を構造化する。

6. 入力要件

6.1 Source Corpus

  • ローカルフォルダ（再帰走査）

  • 明示的なファイル一覧

  • 将来拡張としてURLリスト、指定URL以下、SharePointサイト／ライブラリ

  • PDF、DOCX、PPTX、XLSX、Markdown、HTML、TXT、CSV、JSONを主要対象とする

sources:
- path: ./documents
recursive: true
- list: ./files.txt

include:
- "**/*.{pdf,docx,pptx,xlsx,md,html,txt,csv,json}"
exclude:
- "**/~$*"
- "**/.git/**"

6.2 Usage Intent

利用目的は後から追加・変更・削除でき、同じEvidence IR・Semantic IRから複数の目的別成果物を再生成できなければならない。

id: design-review-assistant
goal: 設計成果物が社内標準を満たすか確認する
users:
- designer
- reviewer
tasks:
- レビュー要否を判定する
- 必要な承認者を特定する
- 違反規則と根拠を提示する
questions:
- この変更にはレビューが必要か
- 誰が承認するか
- 例外承認は可能か
requirements:
evidence_required: true
temporal_scope_required: true
unresolved_conflicts_allowed: false

6.3 任意入力

  • 組織・分野固有の用語集、既存データモデル、既存オントロジー。

  • 正式資料、参考資料、旧版、草案などの権威性ヒント。

  • 抽出したい知識の例、答えられるべき質問、反例。

  • Parser、LLM、Skill、出力形式、セキュリティに関する設定。

7. 概念アーキテクチャと中間体系

図2　FRAGARACHの中間体系

7.1 Source Manifest

原本の所在、ハッシュ、サイズ、更新日時、形式、取得経路、解析状態を管理する。原本の追加・変更・削除を検出し、ビルドグラフの起点とする。

7.2 Parsed Document / Evidence IR

文書解析結果と根拠単位を保持する。目的に依存せず広く保存し、後から利用目的が増えても再解析を最小化する。

  • 見出し・段落・表・スライド・シート・セル範囲・画像領域

  • ページ、節、スライド番号、シート名、セル座標、Markdown行

  • 原文、解析器、解析器版、警告、抽出信頼度

7.3 Domain Schema

資料群と利用目的から、その分野で想定されるエンティティ、関係、イベント、属性、制約を提案・編集・版管理する。一般クラスの固定ではなく、「この用途・資料群では何が対象として現れ、それらはどう結び付くか」を表す。

entity_types:
- id: design_change
label: 設計変更
- id: review_finding
label: レビュー指摘
attributes: [severity, status]

relation_types:
- id: requires_review
source: design_change
target: review
- id: blocks_approval
source: review_finding
target: approval

7.4 Semantic IR / Knowledge Graph

実際に抽出された実体、関係、イベント、Claimを保持する。企業文書から得た記述は最初から確定事実とせず、根拠、適用範囲、時期、権威性、状態を持つClaimとして扱う。

id: claim-1042
type: rule
subject: major_design_change
predicate: requires_approval
object: chief_engineer
scope:
organization: development-division
validity:
valid_from: 2025-04-01
status: candidate
confidence: 0.87
evidence:
- source_id: doc-0012
page: 12
section: "4.3"

7.5 Purpose View / Compilation Profile

利用目的ごとに、必要なエンティティ・関係、完全性条件、整合性条件、検索単位、回答契約、評価条件を定める。Domain SchemaとSemantic IRを目的に応じて射影したビューである。

8. Refinement Pipeline

工程 処理内容
1. Inventory ファイル走査、種別、ハッシュ、日時、重複候補、処理可否を記録する。原則LLM不要。
2. Parse Rust内蔵Parserまたは外部Document AIで共通文書構造へ変換する。
3. Structure 見出し、段落、表、ページ等をEvidence Unitへ分割し、原文位置を保持する。
4. Purpose Analysis 利用目的から質問、必要な判断、想定エンティティ、関係、完全性・整合性条件を提案する。
5. Schema Proposal 資料サンプルを参照し、仮説Domain Schemaを提案・統合・編集可能にする。
6. Extract SchemaとIntentに基づき、実体、関係、Claim、規則、手順、例外を構造化抽出する。
7. Resolve 同義語、表記揺れ、同一実体、重複文書、版関係を推定する。
8. Reconcile 補完、競合、時間差、正式／非正式、未決定を区別し、無理に一つへ統合しない。
9. Validate 根拠一致、完全性、構造・意味・時間・権威・業務・目的適合性を検証する。
10. Emit Knowledge Buildを生成し、任意の下流へExporterで供給する。

9. 機能要件

9.1 ソース・台帳管理

ID 要件 優先度 検証方法
FR-SRC-001 ローカルフォルダを再帰走査し、対象ファイルをSource Manifestへ登録できること。 Must フォルダ投入で台帳が生成される。
FR-SRC-002 ファイルパスを列挙した一覧ファイルを入力できること。 Must 一覧に含まれるファイルのみ登録される。
FR-SRC-003 パス、形式、サイズ、更新日時、内容ハッシュ、取得時刻を保存すること。 Must manifestとDBを確認する。
FR-SRC-004 完全重複を内容ハッシュで検出すること。 Must 同一ファイル複製を一群として表示する。
FR-SRC-005 追加・変更・削除を検出し、前回ビルドとの差分を記録すること。 Must 変更前後の差分レポートを確認する。
FR-SRC-006 未対応・破損・暗号化ファイルは全体処理を止めず警告として隔離すること。 Must 異常ファイルを混在させて完走する。

9.2 文書解析

ID 要件 優先度 検証方法
FR-PRS-001 Parserを交換可能な共通インターフェースとして実装すること。 Must BuiltinとHTTP Parserを差し替えられる。
FR-PRS-002 Markdown、TXT、HTML、CSV、JSONはRust内蔵処理を基本とすること。 Must 外部サービスなしで変換できる。
FR-PRS-003 Office文書・通常PDFはRust系Parserを利用できること。 Must DOCX/PPTX/XLSX/PDFの代表文書が解析できる。
FR-PRS-004 複雑PDF、OCR、表中心文書をDocling等の外部HTTPサービスへ委譲できること。 Should 設定したendpointで再解析できる。
FR-PRS-005 解析結果を人間確認用Markdownと構造化Parsed Documentの両方で保存すること。 Must parsed/*.mdとDB/JSONを確認する。
FR-PRS-006 ページ、節、スライド、シート、セル等、取得可能な原本位置を保持すること。 Must 抽出知識から原本位置へ遡れる。
FR-PRS-007 解析品質を評価し、低品質文書・ページを警告または高精度Parser候補として示すこと。 Should 品質レポートに候補が出る。

9.3 利用目的管理

ID 要件 優先度 検証方法
FR-INT-001 利用目的をYAML等の機械可読形式で定義できること。 Must intentファイルを読み込める。
FR-INT-002 目的、利用者、タスク、質問、証拠要件、時点要件、競合許容条件を保持できること。 Must UsageIntentスキーマ検証を通る。
FR-INT-003 LLMが自由文からUsage IntentとCompetency Question候補を提案できること。 Should 提案内容を編集して保存できる。
FR-INT-004 同じSource Corpusに複数のUsage Intentを登録できること。 Must Onboardingと監査を併存できる。
FR-INT-005 Usage Intentを版管理し、変更差分をビルドグラフへ反映すること。 Must 旧版と新版の再現ビルドが可能。

9.4 Domain Schema提案・管理

ID 要件 優先度 検証方法
FR-SCH-001 利用目的と資料サンプルから想定エンティティ型を提案すること。 Must 根拠件数付き候補が生成される。
FR-SCH-002 エンティティ間の関係型、方向、引数型を提案すること。 Must source/targetを持つ関係候補が出る。
FR-SCH-003 業務イベント、状態遷移、プロセスを提案できること。 Should イベント・前後関係が表現できる。
FR-SCH-004 属性、必須性、値域、時点、適用範囲候補を提案すること。 Should 属性制約がSchemaへ保存される。
FR-SCH-005 各Schema候補に支持根拠、出現件数、反例、提案理由を付与すること。 Must 根拠のない候補を区別できる。
FR-SCH-006 Schemaを人間が追加、修正、統合、却下、承認できること。 Must YAML編集またはCLIで状態変更できる。
FR-SCH-007 Schema変更の互換性と影響範囲を記録すること。 Should 関係分割時に再抽出対象が示される。

9.5 知識抽出・根拠管理

ID 要件 優先度 検証方法
FR-EXT-001 Schemaに基づきエンティティ実体を抽出すること。 Must entity instanceがJSONLへ出る。
FR-EXT-002 関係、イベント、属性値を構造化抽出すること。 Must relation/eventが出力される。
FR-EXT-003 規則、手順、例外、定義、判断条件をClaimとして抽出できること。 Must Claimにtypeとpredicateが付く。
FR-EXT-004 すべてのClaimと関係に一つ以上のEvidence Unitを関連付けること。 Must 根拠なしの候補はinvalid/diagnostic扱い。
FR-EXT-005 抽出元文書、原文位置、引用断片、Parser、Skill、モデル、プロンプト版を追跡すること。 Must provenanceを確認する。
FR-EXT-006 抽出結果にconfidenceとcandidate/approved/rejected等の状態を持たせること。 Must 状態遷移が保存される。

9.6 名寄せ・版・整合化

ID 要件 優先度 検証方法
FR-RCN-001 別名、略語、表記揺れから同一エンティティ候補を生成すること。 Must alias clusterを確認する。
FR-RCN-002 同一文書、近似文書、版違い候補を区別すること。 Must duplicate/version groupが出る。
FR-RCN-003 現行、旧版、草案、非公式、参考等の権威性・状態を保持できること。 Must source authorityを検索条件に使える。
FR-RCN-004 相互補完、条件差、時点差、真正な矛盾を区別すること。 Must diagnostic reasonが分類される。
FR-RCN-005 競合を自動的に一つへ潰さず、複数候補と解決に必要な質問を保持すること。 Must conflictsとopen questionsへ出る。
FR-RCN-006 削除資料のみを根拠とする知識をunsupportedへ遷移させること。 Must 削除後も履歴を追える。

9.7 完全性・整合性検証

ID 要件 優先度 検証方法
FR-CST-001 Usage Intentから完全性条件と整合性条件を提案すること。 Must Compilation Profileへ出力される。
FR-CST-002 構造的整合性を検査すること。例：手順に担当者がない。 Must 欠落関係を診断する。
FR-CST-003 意味的整合性を検査すること。例：同語が異なる概念を指す。 Should 曖昧語を診断する。
FR-CST-004 時間的整合性を検査すること。例：廃止規程を現行手順が参照する。 Must 期間競合を診断する。
FR-CST-005 権威的整合性を検査すること。例：正式規程と個人メモが競合する。 Must 優先順位と競合を表示する。
FR-CST-006 業務的整合性を検査すること。例：処理先のない業務フロー。 Should 到達不能・欠落ステップを示す。
FR-CST-007 目的適合性を検査すること。Usage Intentの質問へ根拠付きで答えられるかを評価する。 Must coverageレポートを生成する。
FR-CST-008 診断にはseverity、対象、根拠、理由、修正候補、確認質問を含めること。 Must consistency-reportを確認する。

9.8 増分再コンパイル

ID 要件 優先度 検証方法
FR-INC-001 各成果物間の依存関係をBuild Graphとして保存すること。 Must 依存ノードと入力ハッシュを確認する。
FR-INC-002 Source追加・変更時は影響するEvidence、抽出、検証、Buildのみ再実行すること。 Must 未変更文書のLLM呼出しが再利用される。
FR-INC-003 Usage Intent追加時は既存IRの再利用可否を判定し、不足知識だけ追加抽出すること。 Must Parseを再実行せず新Buildが生成される。
FR-INC-004 Domain Schema変更時は影響する型・関係に限定して再抽出できること。 Should 全件再処理と差分処理を比較する。
FR-INC-005 Parser、Skill、Prompt、Model、Schema、Intentの版をキャッシュキーに含めること。 Must 版変更時のみ該当キャッシュが無効化される。
FR-INC-006 任意の過去Buildをlock情報から再現できること。 Should build.lockで再実行する。

9.9 Knowledge Build・Exporter

ID 要件 優先度 検証方法
FR-BLD-001 目的別Knowledge Buildをディレクトリ成果物として生成すること。 Must 所定のファイル群が出力される。
FR-BLD-002 Domain Schema、entities、relations、claims、evidenceを機械可読形式で出力すること。 Must YAML/JSONLを検証する。
FR-BLD-003 人間向けoverview、整合性レポート、未解決事項をMarkdownで出力すること。 Must Markdownを確認する。
FR-BLD-004 用途に適した検索単位、フィルタ、rerank条件をRetrieval Profileとして出力すること。 Must retrieval-profile.yamlが生成される。
FR-BLD-005 回答必須要素、根拠表示、競合時の挙動をAnswer Contractとして出力すること。 Must answer-contract.yamlが生成される。
FR-BLD-006 Usage Intent由来の評価質問・期待要素・評価ルーブリックを出力すること。 Should evaluation-set.jsonlが生成される。
FR-BLD-007 Markdown、JSONL、SQLiteを標準Exporterとし、他の下流をPluginで追加可能にすること。 Must Exporterを差し替えられる。
FR-BLD-008 特定のRAG・Vector Store・Graph DBを必須依存にしないこと。 Must RAG未導入でもBuildが完了する。

9.10 CLI・操作

ID 要件 優先度 検証方法
FR-CLI-001 npmからグローバルまたはnpxでCLIを起動できること。 Must npm install後に実行できる。
FR-CLI-002 init、add、scan、intent、schema、compile、recompile、report、exportを提供すること。 Must 各commandのhelpとE2Eを確認する。
FR-CLI-003 処理計画、キャッシュ利用、LLM呼出し数、警告を実行前後に表示すること。 Should dry-runとsummaryを確認する。
FR-CLI-004 機械可読なJSON出力モードを提供すること。 Should CIから結果を利用できる。

11.1 CoreとSkillの責務分離

11.2 LLM利用原則

  • Structured Outputを必須とし、Pydantic相当のSchema検証をRust側で行う。

  • 原文に存在しない情報を補完しない。読めない・判断できない場合はunknownとして返す。

  • 抽出と検証は分離し、重要なClaimは別処理または別モデルで根拠一致を確認する。

  • モデル、温度、プロンプト、Skill、入力Evidenceの版を全て記録する。

  • OpenAI互換API等のProvider抽象を持ち、ローカルモデルを含め交換可能にする。

  • 文書全文を一括投入せず、Evidence Unit・文書群・Schema候補ごとに段階処理する。

14. 非機能要件

ID 観点 要件
NFR-001 再現性 同じSource、Intent、Schema、Parser、Skill、Prompt、Modelの版で同等のBuildを再現できること。
NFR-002 追跡可能性 任意のClaim、Relation、Build Artifactから原本と生成処理へ遡れること。
NFR-003 部分失敗耐性 一部ファイル・LLM呼出しの失敗で全Buildを喪失せず、再開・再試行できること。
NFR-004 セキュリティ ローカルファイルを既定で外部へ送信しない。リモートParser／LLM利用は明示設定すること。
NFR-005 プライバシー ログに原文全文・秘密情報を不用意に出さず、保存範囲と匿名化を設定できること。
NFR-006 移植性 npm導入後、対象OSで追加ランタイムなしに基本機能が動くこと。
NFR-007 拡張性 Parser、Skill、LLM Provider、Validator、Exporterを独立に追加できること。
NFR-008 観測性 各段階の件数、時間、キャッシュ率、LLM呼出し、Token、費用、警告を記録すること。
NFR-009 性能 ファイル走査・ハッシュ・差分判定を並列化し、未変更文書の再解析・再抽出を避けること。
NFR-010 可読性 主要な中間成果物をMarkdown、YAML、JSONLとして人間が確認できること。
NFR-011 監査性 自動提案と人間承認を区別し、変更履歴を保存すること。
NFR-012 OSS適合 コア機能をオープンソースで提供できる依存ライセンス構成とすること。

15. MVP範囲

15.1 MVPに含める

  • ローカルフォルダ、ファイル一覧、再帰走査、Source Manifest、ハッシュ、差分。

  • Markdown、TXT、HTML、CSV、JSON、DOCX、PPTX、XLSX、テキストPDFの解析。

  • 外部Docling HTTP Parserの任意接続。

  • 一つ以上のUsage IntentとLLMによるIntent／質問候補提案。

  • エンティティ型、関係型、属性のDomain Schema提案とYAML編集。

  • 実体、関係、Claimの根拠付き抽出。

  • 完全重複、類似、版候補、別名候補、矛盾候補。

  • 構造・時間・権威・目的適合性の基本診断。

  • Knowledge Build、Retrieval Profile、Answer Contractの出力。

  • Source変更およびIntent追加に対する増分再コンパイル。

  • Rust CLIのnpm配布。

15.2 MVPに含めない

  • SharePoint直接同期、URLクローラ、メール／チャットコネクタ。

  • Web UI、グラフ可視化エディタ、複雑な承認ワークフロー。

  • 本番RAG API、Vector Store、Graph DB、MCP Serverの運用。

  • 組織権限の同期、SSO、RBAC。

  • 完全自動の正式知識確定と競合解消。

  • 全形式の高忠実度文書変換。

16. 受入基準

基準 合格条件
AC-01 20〜100件程度の混在文書をフォルダまたは一覧で投入し、失敗ファイルを隔離しながらSource ManifestとParsed Documentを生成できる。
AC-02 利用目的の自由文からUsage Intent、想定質問、エンティティ・関係候補を提案し、人間が編集して保存できる。
AC-03 主要な抽出ClaimとRelationの100%が少なくとも一つのEvidence Unitへ接続される。
AC-04 完全重複、類似文書、版違い、別名候補、矛盾候補がレポートされる。
AC-05 Usage Intentの質問ごとに回答可能性、根拠有無、不足要素を評価できる。
AC-06 新規文書追加後、未変更文書のParseとLLM抽出結果を再利用し、影響範囲だけ更新する。
AC-07 二つ目のUsage Intent追加時、原本文書の再解析なしに目的別Buildを作成できる。
AC-08 Knowledge Buildにdomain-schema、entities、relations、claims、evidence、consistency-report、retrieval-profile、answer-contractが含まれる。
AC-09 任意のClaimからCLIまたは出力ファイルを介して原本パスと位置へ遡れる。
AC-10 npm installまたはnpxで対象OS上にCLIを導入し、Pythonなしで基本処理を実行できる。

18. リスクと未決事項

論点 対応方針
目的への過剰適合 想定外だが重要な情報を落とす可能性。Evidence IRを目的非依存で保持し、Raw Retrievalへの退避経路を残す。
Schema粒度 エンティティを細かくしすぎる／粗くしすぎる。試験抽出と質問Coverageで評価し、人間が編集する。
LLMの非決定性 再現性と品質がモデルに依存する。Structured Output、版記録、キャッシュ、レビューを必須にする。
Parser品質 Markdown化で表・読み順・位置を失う。構造化IRと品質警告を保持し、複雑文書は外部Parserへ委譲する。
真実の確定不能 正式・非公式、旧版・新版、現場運用が競合する。ClaimとConflictとして保持し、確認質問を出す。
コスト 大量文書へのLLM呼出しが高価。段階処理、候補絞り込み、キャッシュ、ローカルモデルを利用する。
名称・商標 FRAGARACHの商標、npm、GitHub、ドメイン利用状況は正式採用前に調査する。
ライセンス 本体ライセンス（MIT/Apache-2.0）とParser・モデル依存ライセンスを決定する。

18.1 未決事項

  • MVP標準のRust文書Parser候補と対応形式。

  • Docling Serveとの正式API契約と変換結果の正規化仕様。

  • Domain Schema候補を提案するサンプリング・反復アルゴリズム。

  • 同一エンティティ・版関係・競合分類の初期閾値。

  • Human reviewをYAML／CLIだけで行うか、軽量ローカルUIを追加するか。

  • CLI名、crate名、npm scope、正式ライセンス。

19. 用語集

用語 定義
FRAGARACH 利用目的と資料群から、根拠付きの知識体系・検索仕様・評価仕様を生成するKnowledge Compiler。
Source Corpus 入力対象となる文書・ファイル・将来的なURLやSharePoint等の集合。
Usage Intent 何に使い、誰が、何を理解・判断し、何に答える必要があるかを表す仕様。
Evidence IR 原文位置を保持した目的非依存の根拠中間表現。
Domain Schema 資料群に想定されるエンティティ、関係、イベント、属性、制約のモデル。
Semantic IR 抽出された実体、関係、Claim、版、競合を保持する意味中間表現。
Claim 資料から抽出された主張。確定事実と決めつけず、根拠、時期、範囲、状態を持つ。
Compilation Profile 目的別の抽出、完全性、整合性、検索、回答、評価条件。
Knowledge Build 特定のSource・Intent・Schema・Skill・Model版から生成された成果物一式。
Retrieval Profile 下流RAGに推奨する検索単位、フィルタ、関係探索、rerank条件。
Answer Contract 回答に必要な要素、根拠要件、競合・不足時の挙動。
Build Graph Source、IR、Schema、Intent、成果物の依存関係を持つ増分再コンパイル用グラフ。

FRAGARACHはRAGを作るのではない。
RAGが問いに答えるために必要な知識を、目的からビルドする。
