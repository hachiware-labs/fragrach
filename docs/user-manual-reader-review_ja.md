# FRAGARACH マニュアル読者レビュー

評価対象: `docs/user-manual_ja.md`（2026-07-28版）  
評価条件: マニュアルから想像できる情報だけを使い、実装、要件書、テストコードは参照しない。

## 読後の理解

FRAGARACHはRAG製品ではなく、RAGへ登録する知識を利用目的別に改善する前処理CLIである。原文をEvidenceへ分け、LLMがClaim候補を抽出し、Rust側が根拠参照、時点、権威性、矛盾、不足を検証する。完成したKnowledge Buildは汎用JSONLとして出せるが、ベクトル化、検索基盤への登録、回答UIは利用者が用意する。

中心機能を最初から最後まで試せることが分かる。`init`、`scan`、Intent検証、`compile`、Warning確認、`recompile`、`export`の関係も追える。通常RAGとの比較結果があるため、「何が改善し、何がまだ改善していないか」も判断できる。

## 良いと感じる点

最も良いのは、価値を過大に説明していないことである。実測では根拠再現率が82.3%から90.6%へ上がり、禁止誤答率が6.3%から0%へ下がった一方、Strict Passは50.0%で同率、回答要素はRaw RAGより低いと明記されている。知識コンパイルが有望だという説明と、回答精度全般では未証明という限界を区別できる。

Warningの扱いも想像しやすい。探索用途なら競合を開示して使えるが、規程案内や自動実行ではErrorへ昇格するという運用判断が示されている。失敗Buildが公開先へ出ず、診断付きで別領域へ保存されるため、前回の正常Buildを壊しにくいことも分かる。

Ollamaへ送る情報、外部endpointを指定した場合の境界、LLMを呼ばない`recompile`、Buildごとのtoken数と処理時間が説明されている。社内文書の試験導入で、機密性と費用を検討する材料になる。

Knowledge BuildをそのままRAGとして宣伝せず、Intent、`as_of`、権威順位、Answer Contractを下流側で実装する必要を明記している点も信頼できる。JSONLを登録するだけでは同じ評価結果にならないことが読み取れる。

## 残る機能上の不足

マニュアルから見て、0.1.0の中心的な縦切りは完成している。一方、実運用へ進む前には次が必要である。

- 未解決Conflictを人が承認し、Evidence付きoverrideとして再利用する仕組み
- PDF、Office、OCRなど、実際の社内資料で多い形式
- 利用中のVector Storeや検索基盤へ渡す公式アダプター
- 大規模コーパスでの増分Claimコンパイル
- 公開ライセンス、npmレジストリ公開、サポート方針
- 人手評価を含む複数モデル・複数コーパスでの品質検証

特にConflict overrideがないことは機能的な不足である。現在は原文、Front Matter、`corpus.yaml`を修正して再実行するため、文書を変えられない組織では判断結果を管理しにくい。

## まだ分かりにくい点

### 下流RAGの実装量

必要な四つの処理は示されているが、実際のJSONL一行と、それを検索メタデータへ写す例がない。Intent ID、適用期間、権威順位、引用をどのフィールドから読むかは、成果物を開いて調べる必要がある。特定製品に依存しない最小JavaScriptアダプターが一つあると、導入工数を見積もりやすい。

### 権威順位と時点の最終判断

「対象時点を絞る」「権威順位を回答判断へ反映する」とあるが、時点と権威性が異なる結論を示した場合の正確な優先順序は利用者向けに十分説明されていない。コンパイラ内のConflict解決順と、下流RAGが再現すべき順序を同じ規則として例示してほしい。

### LLM候補の品質確認

Evidence IDの実在や日付形式をRust側で検証することは分かる。しかし、Evidenceを引用していてもClaimの意味が誤っている場合に、どこまで検出できるかは分からない。`rejected_claims`の意味、抽出Warningの例、サンプリングレビューの推奨方法があるとよい。

### npmの現在位置

npmパッケージ構成があることと、レジストリ未公開であることは明確である。ただし、tarballを別のクリーン環境へ導入する完全なコマンドはない。「npmでインストール可能」という製品目標を評価するには、対応OSごとのCIと公開手順の完了が必要である。

### 性能の見積もり

25文書で約1分から7分半という実測は有用だが、文書数、Evidence数、Intentの広さのどれが時間を支配するかは分からない。現状では、実データの小さな一部を試して測る必要がある。

## 読者としての評価

| 観点 | 評価 | 理由 |
|---|---:|---|
| コンセプトの明確さ | 5/5 | RAGの前工程だと冒頭と手順で一貫して理解できる |
| 試しやすさ | 4/5 | E2E手順はあるがRust、Ollama、ローカルビルドが必要 |
| Warningの安全性 | 4/5 | 公開ポリシーと失敗隔離は明確。overrideは未実装 |
| RAGへの接続性 | 3/5 | 汎用JSONLはあるが公式アダプターはない |
| 品質根拠 | 3/5 | Actual比較はあるが、小規模・単一モデル・LLM判定である |
| 組織導入の準備 | 2/5 | 未公開、UNLICENSED、規模保証とサポート方針がない |

技術検証としては試す価値がある。とくに、旧版、未採用提案、未更新FAQ、担当者欠落が通常RAGで問題になるチームには適している。一方、回答精度を自動的に上げる完成品として導入する段階ではない。現状の強みは、必要根拠の検索と危険な断定を抑える構造を作ることであり、回答の完全性は下流RAGと評価設計に依存する。

## 次に優先したい改善

次の開発では、まずJSONLから評価用RAGを構築する公式の参照アダプターを用意したい。これにより、利用者が`retrieval-profile.yaml`と`answer-contract.yaml`を正しく反映し、マニュアルの評価結果を再現しやすくなる。

その次に、Evidence付きConflict overrideと承認履歴を実装する。最後に、異なる規模の実コーパス、別の回答モデル、人手盲検評価で検証し、検索改善が回答品質へ伝わらない設問を分析する。この三点が揃えば、技術検証から組織導入候補へ進める。
