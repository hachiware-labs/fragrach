# Fragrach コーパス要求定義書

- 文書名: Fragrach コーパス要求定義書
- バージョン: v0.1
- 作成日: 2026-07-28
- 対象製品: Fragrach
- 想定読者: 開発者、評価設計者、コーパス作成者、研究協力者
- 状態: Draft

---

## 1. 文書の目的

本書は、Fragrachの主要ターゲットである「部門に蓄積された過去のナレッジ文書を、十分に整理されていない状態で投入し、利用目的に沿って根拠付きで回答できるようにする」能力を評価するための、テストコーパス要求を定義する。

業種・部門ごとに文書の有力度が変わる具体例と、今後追加するScope、例外、部分改訂、正本性、Lineageの評価Archetypeは[企業文書の有力度と活用ケース](research/enterprise-document-validity-cases_ja.md)を参照する。

Fragrachは通常のRAG基盤そのものではない。利用目的と資料群から、想定されるエンティティ、関係、Claim、Conflict、権威性、適用時点、検索仕様、回答制約をコンパイルする知識ビルドシステムである。

したがって本コーパスは、単純な検索精度だけでなく、以下を評価できなければならない。

1. 雑多な文書群から、目的に必要な知識を抽出できること
2. 重複、旧版、矛盾、非公式資料を区別できること
3. Claim中心の検索とRaw Evidenceの補完を適切に組み合わせられること
4. 根拠、引用、回答要素、禁止事項を正しく扱えること
5. 文書や利用目的の増減に応じて、再コンパイルできること

## 2. 評価対象となる利用シナリオ

### 2.1 主要シナリオ

部門の共有フォルダ、SharePoint、ファイル一覧などに保管された過去文書をまとめて取り込み、部門の業務、規則、手順、障害対応、意思決定、役割、用語、システムについて質問する。

想定利用者は以下とする。

- 新任者
- 部門メンバー
- プロジェクトリーダー
- 設計・レビュー担当者
- 障害対応担当者
- 管理職
- 監査・品質担当者

### 2.2 代表的な質問

- 現在の設計レビュー承認者は誰か
- 緊急配備後のレビュー期限は何日か
- 重大指摘が残っている場合に承認できるか
- 過去のある時点では、どの規則が適用されていたか
- この障害の指揮役と報告責任者は誰か
- 類似障害では、どの暫定対応と恒久対策が行われたか
- この仕様が採用された理由は何か
- どの文書が現行の正式版か
- 資料間に矛盾がある場合、何が未解決か
- 該当情報が存在しない場合、回答を控えられるか

## 3. コーパス設計原則

### 3.1 一貫した企業世界を作る

各文書を独立した例題として作るのではなく、同じ企業、部門、人物、製品、プロジェクト、規程、システムが複数の文書へ横断して登場する一貫した世界を構築する。

推奨する架空組織の単位は、1社の1部門とする。

例:

```text
青羽工業株式会社
└── 開発運用部
    ├── 設計レビューグループ
    ├── 障害対応グループ
    ├── 品質保証グループ
    └── プラットフォームグループ
```

### 3.2 Raw Corpusを正本とする

Raw Corpusは、文書、表、FAQ、議事録、障害報告などの原典である。

Fragrachが生成するClaim、Conflict、Domain Schema、EvidenceはRaw Corpusから派生した中間成果物として扱う。

### 3.3 正解を一意にできない問題を含める

実際の部門文書には、以下が存在する。

- 複数の現行版候補
- 規程と運用ガイドの食い違い
- 状態や適用時点が不明な文書
- 正式決定前の案
- 個人メモ
- 過去には正しかったが現在は失効した記述

コーパスには、Fragrachが勝手に解決してはならない矛盾を意図的に含める。

### 3.4 目的別に正解構造を変える

同じRaw Corpusに対して、複数のIntentを定義する。

例:

- design-review
- incident-response
- onboarding
- project-history
- compliance-audit

Intentごとに、必要なエンティティ、関係、回答要素、禁止事項、整合性条件を変える。

## 4. コーパス種別

Fragrachの標準評価では、以下の5種類の単独コーパスと、それらを統合した混合部門コーパスを用意する。

## 4.1 規程・手順型

### 含める文書

- 規程
- 標準
- ガイドライン
- 作業手順書
- チェックリスト
- 承認フロー
- 補足通知
- 例外運用通知
- 新旧版
- 下位組織向けローカルルール

### 評価対象

- 現行版の特定
- 権威順の適用
- 有効期間
- 規則と例外
- 承認者
- 禁止事項
- 矛盾検出
- 厳格公開ゲート

## 4.2 障害・問い合わせ型

### 含める文書

- 障害報告書
- インシデント記録
- 問い合わせチケット
- FAQ
- 暫定対応メモ
- 恒久対策報告
- 運用手順
- ログ抜粋
- 連絡網
- 障害後レビュー

### 評価対象

- 症状、原因、処置の分離
- 類似障害の識別
- 暫定策と正式手順の区別
- 現在の指揮役、担当者、報告責任者
- 時系列の復元
- 古いFAQの誤用防止

## 4.3 プロジェクト・意思決定型

### 含める文書

- 企画書
- 要件定義書
- 設計書
- 会議議事録
- ADR
- 課題管理票
- メール・チャット記録
- 採用案と不採用案
- 結果報告
- 振り返り

### 評価対象

- 正式決定と検討案の区別
- 誰が、いつ、何を決めたか
- 決定理由
- 前提条件
- 後続成果物との関係
- 複数文書をたどる多段推論

## 4.4 組織・Onboarding型

### 含める文書

- 組織図
- 役割分担表
- 業務概要
- システム一覧
- 用語集
- 教育資料
- 担当者一覧
- 引き継ぎ資料
- 個人作成メモ
- 社内FAQ

### 評価対象

- 人、役割、組織、業務の名寄せ
- 略称、旧部署名、旧役割名
- 正式責任と実態担当の区別
- 属人的知識
- 情報不足時の回答抑制
- 連絡先と担当の鮮度

## 4.5 表・一覧・帳票型

### 含める文書

- Excel管理表
- CSV
- 仕様一覧
- イベント列
- 申請一覧
- PowerPoint内の表
- 定型報告書
- 同一テンプレートの大量文書

### 評価対象

- 表見出しとセルの関係
- 行・列単位のEvidence Bundle
- 一覧の完全性
- 数値、日付、単位
- 類似帳票の取り違え
- 同型文書が多い場合の検索劣化

## 4.6 混合部門コーパス

5種類の文書を同じ企業世界へ統合する。

同じ人物、システム、製品、規程、障害、プロジェクトが複数の文書種別に登場しなければならない。

混合部門コーパスを最終的な主評価コーパスとする。

## 5. 規模要件

文書数だけでなく、Evidence数、Rawチャンク数、総文字数、ファイル容量を記録する。

| 段階 | 文書数 | Evidence目安 | 主な用途 |
|---|---:|---:|---|
| XS | 25〜50 | 300〜700 | 単体機能・高速回帰 |
| S | 100 | 800〜1,500 | PR・日常開発 |
| M | 500 | 4,000〜8,000 | 部門サブ領域・Nightly |
| L | 2,000 | 15,000〜30,000 | 部門全体・Release |
| XL | 8,000〜10,000 | 60,000〜120,000 | 性能・余裕度 |

### 5.1 入れ子構造

各規模は可能な限り入れ子にする。

```text
XS ⊂ S ⊂ M ⊂ L ⊂ XL
```

これにより、規模増加による劣化と、内容難化による劣化を分離する。

### 5.2 現行評価との対応

- 25文書評価: XS相当
- 47文書評価: XS相当
- 100文書Medium評価: S相当

次の主要到達点はMの500文書とする。

## 6. ノイズ・品質劣化要件

同一の企業世界に対し、Clean、Typical、Harshの3段階を用意する。

## 6.1 Clean

- 正式文書中心
- 版情報が明確
- 重複が少ない
- 矛盾なし
- メタデータがほぼ完全

用途: 基本機能と上限性能の確認。

## 6.2 Typical

部門文書の現実的な状態を模す。

目安:

| ノイズ種別 | 割合・件数目安 |
|---|---:|
| 完全重複 | 5〜10% |
| 類似・版違い | 10〜20% |
| 旧版・失効文書 | 10〜20% |
| ドラフト・個人メモ | 10〜20% |
| 無関係・誤配置 | 10〜20% |
| メタデータ欠落 | 10〜30% |
| 意図的矛盾 | Intentごとに2〜5件 |

## 6.3 Harsh

- 複数の現行版候補
- 権威性が不明
- 旧部署名・略称が大量
- 同じテンプレートの文書が多数
- 矛盾したFAQ
- 決定前の案と正式資料が混在
- 重要情報が一文書にしかない
- 時点が明記されない
- 答えが存在しない質問
- 誤解を誘う類似記述

用途: 安全性、公開ゲート、回答抑制、fallback制御の確認。

最低限、以下の形式を含める。

| 形式 | S | M | L/XL |
|---|---:|---:|---:|
| Markdown / Text | 必須 | 必須 | 必須 |
| HTML | 必須 | 必須 | 必須 |
| PDF（テキスト） | 必須 | 必須 | 必須 |
| PDF（スキャン） | 任意 | 必須 | 必須 |
| DOCX | 必須 | 必須 | 必須 |
| XLSX / CSV | 必須 | 必須 | 必須 |
| PPTX | 任意 | 必須 | 必須 |
| JSON / XML | 任意 | 任意 | 必須 |
| メール形式 | 任意 | 任意 | 推奨 |

### 7.1 複雑文書

M以上では以下を含める。

- 多段組みPDF
- 表がページをまたぐPDF
- 図と本文が混在する資料
- 複数シートを持つExcel
- ノート付きPowerPoint
- OCR品質が低いスキャン

```yaml
  - shared/design-review-standard.pdf

  - design-review
```

## 9. 意図的に埋め込む知識問題

各コーパスは、以下の問題を含む。

### 9.1 重複・Alias

- 完全重複
- ファイル名だけ異なるコピー
- 共有フォルダ上の複製
- 内容の一部だけ更新されたコピー

期待動作:

- 検索では同一Evidenceとして扱える
- 引用では正式原本へ正規化できる

### 9.2 版・時点

- 旧版と新版
- 改訂通知
- 移行期間
- 過去案件にだけ適用される旧規則
- 現行質問で旧版を使ってはいけない例

### 9.3 権威性

- 正式規程
- 運用ガイド
- 会議メモ
- 個人メモ
- FAQ
- ドラフト

期待動作:

- 正式性を検索順位へ反映する
- 非公式資料を現行結論へ使わない

### 9.4 Conflict

- 同じ対象に異なる期限
- 異なる承認者
- 旧版と現行版の混同
- 正式規程と実運用の食い違い

期待動作:

- 矛盾を隠さない
- 厳格Intentでは公開を停止する
- Warning Intentでは未解決として出力する

### 9.5 Claim抽出漏れ

正解情報の一部はClaimへ抽出されず、Raw Evidenceにのみ残す。

期待動作:

- Claim中心検索の被覆不足を検出する
- 必要時のみEvidence fallbackで救済する

### 9.6 表のEvidence Bundle

一つの回答に必要な複数要素を、同じ表の異なるセルへ配置する。

期待動作:

- 単一セルではなく、意味的に不可分な行・列・表領域をまとめて取得する

### 9.7 情報不在

質問に答える情報が存在しないケースを含める。

期待動作:

- 推測で回答しない
- 情報不足を明示する
- 必要な追加資料や確認事項を提示する

## 10. Intent要件

各Intentは以下を定義する。

```yaml
id: design-review
goal: 設計レビューの要否、承認条件、例外を根拠付きで回答する
users:
  - designer
  - reviewer
required_entity_types:
  - design_change
  - review
  - finding
  - approver
  - policy
required_relations:
  - requires_review
  - approved_by
  - blocks_approval
  - governed_by
required_answer_slots:
  - conclusion
  - conditions
  - exception
  - effective_period
  - evidence
unresolved_conflicts_allowed: false
```

### 10.1 標準Intent

最低限、以下を用意する。

1. design-review
2. incident-response
3. onboarding
4. project-history
5. compliance-audit

### 10.2 Intentの独立性

同じRaw Corpusから、Intentごとに別のKnowledge Buildを生成できなければならない。

## 11. 質問セット要件

## 11.1 質問分類

最低限、以下の10種類を含める。

1. 単一文書の事実
2. 人・役割・責任
3. 現行規則・最新版
4. 過去時点の規則
5. 規則と例外
6. 複数文書統合
7. 時系列・意思決定経緯
8. 矛盾の開示
9. 一覧・必須項目の完全回答
10. 情報不在・回答禁止

## 11.2 Fragrach固有の回帰質問

以下を固定回帰セットに含める。

- Claimにない正解をEvidence fallbackで取得する質問
- 旧版Evidenceを取得しても現行結論に使ってはいけない質問
- Aliasから正式原本を引用する質問
- Conflictがあるため一意に断定してはいけない質問
- 直接記載があるのに「記載なし」と回答しやすい質問
- 表の複数セルをそろえないと回答できない質問

## 11.3 問題数

| テスト種別 | 問題数 |
|---|---:|
| Smoke | 24〜30 |
| Nightly | 80〜120 |
| Release | 200以上 |
| XL固有 | 追加50以上 |

標準評価セットの最初の到達点は100問とする。

推奨内訳:

- 複数文書: 20問以上
- 時間・版: 15問以上
- 矛盾・権威: 15問以上
- 情報不在・禁止: 15問以上
- 表・一覧完全性: 10問以上

---

## 12. 正解ラベル要件

各質問は、単一の期待回答文ではなく、構造化した正解を持つ。

```yaml
question_id: DR-001
intent: design-review
question: 緊急配備後の事後レビュー期限は何日か
as_of: 2026-07-01
required_answer_elements:
  - review_is_required
  - deadline
  - starting_point
  - conflict_disclosure
expected_behavior: disclose_conflict
prohibited_conclusions:
  - deadline_is_definitively_3_days
  - deadline_is_definitively_5_days
gold_evidence:
  - document_id: doc-0042
    section: "4.2"
  - document_id: doc-0061
    section: "2.1"
accepted_citations:
  - evidence_group: emergency-review-deadline
```

### 12.1 ラベル項目

- required_answer_elements
- optional_answer_elements
- prohibited_conclusions
- expected_behavior
- gold_evidence
- accepted_aliases
- canonical_citation
- valid_time_scope
- authority_requirements
- conflict_expectation

## 14. 比較方式

最低限、以下を比較する。

1. Raw RAG
2. Oracle compiled
3. Actual Claim baseline
4. Actual Evidence only
5. Actual full Evidence fallback
6. Claim / Evidence固定比率Hybrid
7. 被覆不足検出型の段階検索

### 14.1 既定候補

Fragrachの既定参照方式は、以下を目標とする。

```text
Claim検索
  ↓
Alias正規化・重複除去
  ↓
関連Conflict取得
  ↓
回答スロット被覆判定
  ↓
Claim-linked Evidence展開
  ↓
不足時のみScoped Evidence検索
  ↓
時点・権威・イベント構造で再順位付け
```

## 15. 差分再コンパイル用テスト

静的評価とは別に、以下の変更シナリオを用意する。

1. 新しい正式規程を追加
2. 旧版を削除
3. 担当部署を変更
4. 矛盾文書を追加
5. 矛盾を解消する通知を追加
6. 新しいIntentを追加
7. 既存Intentの回答要件を変更
8. Claim抽出Skillを更新
9. パーサーを更新
10. LLMモデルを変更

### 15.1 評価項目

- 影響範囲だけが再処理されたか
- 古いClaimが失効したか
- Conflict状態が更新されたか
- 公開ゲートが正しく変化したか
- 既存質問の非意図的回帰がないか
- 再コンパイル前後の差分が説明可能か

## 16. テスト実行階層

## 16.1 Pull Request

- S: 100文書
- 規程型、障害型
- 24〜30問
- 検索評価を中心とする
- 回答評価は代表10問程度

## 16.2 Nightly

- M: 500文書
- 5種類の混合部門コーパス
- 100問
- コンパイル、検索、回答を実行
- 複数seedまたは3回反復

## 16.3 Weekly / Release

- L: 2,000文書
- 混合部門コーパス
- 200問以上

## 18. データ生成方針

### 18.1 人工生成と手作業の併用

- 文書本文の初稿はLLM生成を利用できる
- 企業世界、時系列、人物、規程、正解関係は構造化データから生成する
- 正解ラベルは機械生成後に人間が確認する
- 矛盾、旧版、Alias、情報不在は意図的に注入する

### 18.2 正解から文書を生成する

可能な限り、先に企業世界の正解モデルを作り、その状態から各文書を生成する。

```text
World Model
   ↓
時点別の事実・規則・決定
   ↓
文書生成
   ↓
ノイズ・旧版・矛盾の注入
```

これにより、質問の正解、適用時点、正式性を追跡しやすくする。

### 18.3 自然な不整合を作る

単純に正解文の否定を置くのではなく、以下のような現実的な不整合を作る。

- 更新通知が一部の文書へ反映されていない
- FAQだけ古い
- 議事録では決定したが規程改訂が遅れている
- 部署再編後も旧部署名が残る
- 共有コピーだけが更新されている

## 20. 安全・ライセンス要件

- 実在企業の機密情報を使用しない

## 24. 要約

Fragrachの標準コーパスは、単なる文書検索用データセットではない。

以下を同時に評価できる、目的駆動の企業知識コーパスでなければならない。

- 文書の玉石混交
- 版、時点、権威性
- ClaimとRaw Evidenceの役割分担
- 矛盾と公開ゲート
- エンティティ、関係、回答要素
- 情報不足時の抑制
- 利用目的の違い
- 差分再コンパイル

標準構成は、5種類の単独コーパスと1種類の混合部門コーパス、4〜5段階の規模、3段階のノイズとする。

直近の最重要成果物は、以下である。

1. 500文書の混合部門コーパス
2. 100問の構造化質問セット
3. Typicalレベルの重複、旧版、矛盾、無関係文書
4. Claim中心検索と段階Evidence fallbackを比較できる正解ラベル

これをFragrachのMコーパス標準とする。
