# 長文企業文書によるRAG比較計画

短文中心のP1評価では、LightRAGとCogneeが一文書一チャンクとなり、top 5だけで全12文書の約4割を参照できた。この条件は外部OSSの導入確認には使えるが、企業文書検索の主要な精度根拠にはしない。今後は、短文と長文が混在し、Gold根拠が文書の途中にも現れる長文コーパスを主要比較に使う。

## 評価対象

長文コーパスは、製造・製品設計、ソフトウェア・SRE、金融・コンプライアンス、医療・品質薬事の4部門RAGを収録する。各部門は6用途、3更新系列、72文書、36質問を持ち、全体では288文書・144質問となる。

72件の中心文書を長文化し、関連する216件のFAQ、承認記録、草案、追補、実施ログなどは短文のまま残す。長文化するのは、現行規程、技術仕様、決裁議事録、標準手順、最終障害報告、基本契約である。生成前に文書骨子を固定し、評価対象のGold文は生成モデルへ書き換えさせず、文書の前半・中央・後半へ決定的に配置する。Ollamaは背景や参照上の注意を生成する。入力にない日付、数値、製品コードを含む文は除去し、除去後に章として十分な長さが残らない場合だけ、その章を再生成する。

## 二つの比較

製品としての使い方と、検索方式そのものの寄与を分けて測る。

標準設定比較では、各方式が通常採用する索引単位と検索処理を使う。これにより、導入したときに得られる実用上の品質、構築時間、質問時間を比較できる。ただし、チャンク粒度の違いも結果へ含まれる。

統一チャンク比較では、`o200k_base`で作った同一の原文チャンクを全方式へ渡す。512 tokensでは64 tokens、1,024 tokensでは128 tokensを重複させる。Markdownの見出しと段落境界を維持し、Gold段落を途中で切らない。この比較で、Dense検索、Graph検索、Fragrachのコンパイル情報が同じ原文単位に対して与える差を確認する。

| 条件 | 標準設定での検索単位 | 統一チャンク条件で確認するもの |
|---|---|---|
| Raw Tuned BM25 | 最大1,024文字の原文chunk | 日本語文字2-gram BM25の基準値 |
| Ruri Dense | 原文chunkの埋め込み | 言い換えと意味類似による増分 |
| Raw Hybrid | BM25とRuriを重み付きRRFで統合 | Sparse比率0.85と0.90の差 |
| LightRAG Naive | LightRAGが作る原文chunk | 同じRuri Dense実装との差 |
| LightRAG Hybrid | Entity、Relation、原文chunk | Graphと質問時keyword抽出の増分 |
| Fragrach Relation Dossier | Claim、Relation、Conflict、両側原文 | 目的、権威、時点、文書関係を事前コンパイルする増分 |

主要比較では質問の利用目的が既知である前提をRaw側にも与え、同じ部門・同じ用途の12文書を検索対象にする。Fragrachだけが目的を知る弱い基準にはしない。部門全72文書を一つの索引にする条件は、目的分類が利用できない運用の副次評価として残す。

## 指標と判定

検索品質の主要指標はR@5とする。R@10、R@20は必要根拠が候補集合に残っているかを確認する補助指標である。企業文書の更新系列を扱うため、通常の根拠再現率だけでなく、版関係、矛盾の両側、不要候補も同時に測る。

| 優先度 | 指標 | 判定の意味 |
|---:|---|---|
| 1 | R@5 | 少数の回答資料へ必要根拠が集まるか |
| 2 | Conflict両側@10 | 正式文書と競合文書を同時に取得できるか |
| 3 | Relation Path@10 | 旧版・改訂・承認・実施記録の両端を取得できるか |
| 4 | Distractor@5 | 回答を迷わせる不要chunkが上位を占めないか |
| 5 | 根拠/1,000 tokens | context量に対して有効な根拠が多いか |
| 6 | Gold位置別再現率 | 文書前半だけでなく中央・後半の根拠を取得できるか |
| 7 | 構築時間・LLM tokens・質問時間 | 品質差に必要な前処理費用と待ち時間は妥当か |

top-k固定だけでなく、1,500、2,500、4,000 tokensの固定context budgetでも採点する。LightRAGの短文P1のように、一つの検索単位が多くの原文を含む方式を過大評価しないためである。

検索条件を絞った後、同じLuna回答モデルで最終回答を生成する。最終判定では引用再現率、回答要素再現率、禁止誤答率、Strict Passを測る。検索R@5が高くても禁止結論を回避できない方式は採用しない。

## 実行順序

まず、512 tokensと1,024 tokensの統一チャンクを作り、全144質問でBM25、Ruri Dense、Raw Hybridを測る。この段階では回答LLMを使わない。次に、上位のチャンクサイズとRaw検索条件を固定し、LightRAG NaiveとHybridを比較する。LightRAGはNaiveとHybridの差がGraphの寄与であり、Naiveが同率以上ならHybridの追加費用を正当化しない。

Fragrachは同じ4部門・6用途をLunaでコンパイルし、Rawの最良条件、LightRAGの最良条件、Relation Dossierを比較する。固定context budgetでRawを上回り、ConflictとRelationの指標を悪化させない条件だけを最終回答評価へ進める。

長文生成、コンパイル、外部OSSのKnowledge Buildはそれぞれ時間がかかるため、文書単位または用途単位でキャッシュし、成功済みの処理を再利用する。生成失敗、導入上の修正、採用しなかった実行も評価記録へ残す。

## 現在の位置づけ

短文P1のLightRAG R@5 100%は、外部OSS比較を実行できた証拠として維持する。一方、「LightRAGがRaw Tunedより高精度」「FragrachがLightRAGより高精度」といった製品上の結論は、この長文比較が完了するまで確定しない。
