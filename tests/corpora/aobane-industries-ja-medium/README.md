# 青羽精機 社内文書コーパス M

このコーパスは、FragrachがRAGへ投入する前の文書群をどのように整理し、根拠付き知識へ変換できるかを検証するための架空データです。登場する企業、人物、製品、規程、連絡先はすべて架空であり、実在する組織とは関係ありません。

コーパス全体の目的、規模、ノイズ、形式、Intent、質問、正解ラベル、評価指標、再現性、受入基準は、[Fragrach コーパス要求定義書](../../../docs/corpus-requirements_ja.md)を正本とします。

## 想定する企業と部署

青羽精機株式会社は、製造業向けの設備監視サービス「AobaWatch」を開発・運用しています。コーパスには、全社方針を管理する経営管理部、設計・リリース基準を管理する品質保証部、製品を実装する製品開発部、本番環境とセキュリティを担う情報システム部、顧客窓口となるカスタマーサポート部の文書が含まれます。

部署ごとに文書の目的と権威が異なります。正式規程だけでなく、旧版、部署内ガイド、FAQ、議事録も含めることで、文字列が似ているだけでは正しい結論を選べない状態を再現しています。

現在のSource Corpusは500文書、206,860文字、Evidence Unit概算5,423件です。従来の100文書を入れ子のS部分集合としてそのまま保持し、構造化した企業世界から400文書を追加しました。追加分は、規程・手順、障害、プロジェクト・意思決定、Onboarding、表・一覧の5群を各80文書含みます。

追加400文書のうち370文書は、構造化データで固定した事実へOllama生成の短い導入文を組み合わせています。残る30文書は、共有フォルダ上の完全重複を意図して作ったコピーです。旧版、未更新FAQ、ドラフト、個人メモ、空テンプレート、欠落項目を同じ企業世界へ混ぜ、top-kの競争と文書状態の判定を難しくしています。

## Smallとの関係

`aobane-industries-ja`は高速な回帰試験用として固定します。Mは既存の16問を変更せず、M固有の84問を加えた100問で評価します。規模増加による回帰は先頭16問、M固有の機能範囲は追加84問で分けて確認できます。

## 旧100文書版の初期検索値

100文書時点のコンパイル前Raw RAGは511チャンクでした。Smallと同じ日本語文字n-gram BM25と16問で測定した根拠再現率は、top 5が82.3%、top 10が91.7%、top 20が97.9%でした。この値は500文書版の基準値ではなく、S部分集合との比較用に残しています。500文書・100問の値は、生成後のベンチマークで改めて記録します。

## ディレクトリ

- `sources/`: Fragrachへ入力する文書群
- `world/`: 組織、人物、システム、プロジェクト、時系列の正本
- `intents/`: 同じ文書群へ適用する利用目的
- `gold/`: M固有質問のEvidence、Alias、Version、Conflict、回答ラベル
- `generation/`: Ollamaの生成条件と再現性レポート
- `ground-truth/expected.json`: 抽出、名寄せ、版、競合、欠落の主要な期待値
- `scenarios/`: 増分再コンパイルを試す追加・変更・削除シナリオ
- `corpus.yaml`: 入力範囲と権威性ヒントの例

`sources/`だけをSource Corpusとして走査してください。`ground-truth/`と`scenarios/`は正解や操作手順を含むため、通常の抽出対象には含めません。

## 含まれるテスト要素

文書間には、意図的に次の状態を作っています。

- 同じ規程の現行版と旧版
- 同じ規程が三世代にわたって逐次改訂された履歴
- 内容が同一でパスだけ異なる文書
- 正式規程と部署内FAQの競合
- 提案、レビュー承認、実装完了へ進む変更記録
- 実装済みの内容と食い違う未更新FAQやチートシート
- 決定事項ではない議事録上の提案
- 略語と正式名称による同一役割の表記揺れ
- 適用開始日が異なる規則
- 担当者が書かれていないチェック項目
- 例外手続と事後レビュー
- 別部署の文書による補完
- 本番とサンドボックスで異なるアクセス承認と有効時間
- 顧客エクスポート、ログ、バックアップ、社内CSVで異なる保持期間
- 製品変更、コード、供給元、全社リスクで異なるレビューと承認
- 正式な決定と、議事録・検討メモ・単発の実施記録の区別
- 契約承認規程、供給元監査標準、配備ガイド、鍵更新標準の版更新
- 初報、状況更新、最終報へ進む障害記録
- 同じCSVやエクスポートという語を使う顧客向け、社内分析、監査、会計の区別
- 未承認のお知らせ案と承認済み案内
- 未決の保存期間を複数含む会議記録

既存100文書の期待値は`ground-truth/expected.json`、M追加分の構造化ラベルは`gold/`を正本とします。本文の自然な言い回しをOllamaが生成しても、期限、役割、原因、決定、正解ラベルは生成モデルへ委ねません。

## 最初の試験

最初は`design-review.yaml`を使い、設計変更にレビューが必要か、誰が承認するか、例外が認められるかをコンパイルします。次に`incident-response.yaml`を追加し、Parsed Documentを再生成せずに障害対応用のKnowledge Buildを作れるか確認します。`data-export-operation.yaml`では、提案から実装までの状態遷移と、実装後も残ったFAQの矛盾を扱います。

増分試験では、`scenarios/incremental/README.md`の手順に従い、文書の追加、現行規程の改訂、根拠文書の削除を順に適用します。

## 未解決矛盾の公開方針

通常の`design-review.yaml`と`incident-response.yaml`は、未解決矛盾が1件でも残ればKnowledge Buildの公開を停止する厳格版です。`design-review-warn.yaml`と`incident-response-warn.yaml`は同じIntent IDと質問を持ちますが、未解決矛盾をWarningと未解決質問として残したまま公開できます。

Mediumの実測では、厳格版の設計レビューは事後レビュー期限の未解決矛盾2件を検出して公開を停止しました。Warning版では矛盾を成果物へ残し、Raw RAGとの評価に使用できました。運用要件に合わせ、決定不能な知識を下流へ渡してよい場合だけWarning版を使ってください。

このコーパスは回帰確認用の小規模fixtureとして保持します。現行の横断評価は[最終評価](../../../docs/evaluations/final-metrics_ja.md)を参照してください。
