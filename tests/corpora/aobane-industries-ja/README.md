# 青羽精機 社内文書コーパス

このコーパスは、FragrachがRAGへ投入する前の文書群をどのように整理し、根拠付き知識へ変換できるかを検証するための架空データです。登場する企業、人物、製品、規程、連絡先はすべて架空であり、実在する組織とは関係ありません。

## 想定する企業と部署

青羽精機株式会社は、製造業向けの設備監視サービス「AobaWatch」を開発・運用しています。コーパスには、全社方針を管理する経営管理部、設計・リリース基準を管理する品質保証部、製品を実装する製品開発部、本番環境とセキュリティを担う情報システム部、顧客窓口となるカスタマーサポート部の文書が含まれます。

部署ごとに文書の目的と権威が異なります。正式規程だけでなく、旧版、部署内ガイド、FAQ、議事録も含めることで、文字列が似ているだけでは正しい結論を選べない状態を再現しています。

現在のSource Corpusは47文書、29,704文字、1,424行（空行を含む）です。初期版の25文書、14,825文字から、正解文書を変えずに文章量を約2倍へ増やしました。追加文書には、同じ「承認」「レビュー」「アクセス」「保持期間」「エクスポート」という語を使いながら、対象環境や業務が異なる内容を含めています。

## ディレクトリ

- `sources/`: Fragrachへ入力する文書群
- `intents/`: 同じ文書群へ適用する利用目的
- `ground-truth/expected.json`: 抽出、名寄せ、版、競合、欠落の主要な期待値
- `scenarios/`: 増分再コンパイルを試す追加・変更・削除シナリオ
- `corpus.yaml`: 入力範囲と権威性ヒントの例

`sources/`だけをSource Corpusとして走査してください。`ground-truth/`と`scenarios/`は正解や操作手順を含むため、通常の抽出対象には含めません。

## 含まれるテスト要素

文書間には、意図的に次の状態を作っています。

- 同じ規程の現行版と旧版
- 同じ規程が三世代にわたって逐次改訂された履歴
- 内容が同一でパスだけ異なる文書
- 正式規程と部署内FAQの競合
- 提案、レビュー承認、実装完了へ進む変更記録
- 実装済みの内容と食い違う未更新FAQやチートシート
- 決定事項ではない議事録上の提案
- 略語と正式名称による同一役割の表記揺れ
- 適用開始日が異なる規則
- 担当者が書かれていないチェック項目
- 例外手続と事後レビュー
- 別部署の文書による補完
- 本番とサンドボックスで異なるアクセス承認と有効時間
- 顧客エクスポート、ログ、バックアップ、社内CSVで異なる保持期間
- 製品変更、コード、供給元、全社リスクで異なるレビューと承認
- 正式な決定と、議事録・検討メモ・単発の実施記録の区別

期待値は網羅的な全文正解ではありません。まず回帰試験に必要な代表的なClaim、Conflict、Alias、Version、Coverageを固定し、実装の成熟に合わせて追加する前提です。

## 最初の試験

最初は`design-review.yaml`を使い、設計変更にレビューが必要か、誰が承認するか、例外が認められるかをコンパイルします。次に`incident-response.yaml`を追加し、Parsed Documentを再生成せずに障害対応用のKnowledge Buildを作れるか確認します。`data-export-operation.yaml`では、提案から実装までの状態遷移と、実装後も残ったFAQの矛盾を扱います。

増分試験では、`scenarios/incremental/README.md`の手順に従い、文書の追加、現行規程の改訂、根拠文書の削除を順に適用します。
