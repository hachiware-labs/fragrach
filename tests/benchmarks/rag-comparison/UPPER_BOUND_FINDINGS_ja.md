# FRAGARACH RAG比較結果

実施日: 2026-07-28

## 結論

Actual Knowledge Buildは、Raw RAGより正解根拠をtop 5へ取得しやすく、禁止された断定も減らした。しかし、回答のStrict Pass率は同率で、必須回答要素の再現率はRaw RAGを下回った。したがって、現段階で確認できたのは検索根拠と安全性の改善であり、回答精度全般が通常RAGを上回ったとは結論できない。

以前のOracle上限実験で必要と判断した、Evidence付きClaim、時点、文書状態、権威順位、Conflict、Intent filterは実装された。Actualの根拠再現率@5はRawの82.3%から90.6%へ8.3ポイント改善した。未採用提案、未更新FAQ、旧版、担当者欠落を扱う質問でも、危険な禁止回答は0件だった。

一方、正しい文書を検索しても、回答モデルが必要な全要素と引用を出すとは限らない。Knowledge Buildだけで回答品質が決まるわけではなく、Retrieval ProfileとAnswer Contractを下流RAGが正しく実行する必要がある。

## 最終比較の条件

- Source Corpus: 架空社内文書25件（完全重複1件を含み、解析文書は24件）
- 固定質問: 16問、4 Usage Intent
- Raw索引: 161文書チャンク
- Oracle索引: 37知識単位
- Actual索引: 142検索単位
- 検索: 日本語文字2-gram・3-gram BM25、top-k 5
- Actual filter: Intent ID、質問の`as_of`
- Actual ranking: `corpus.yaml`の権威順位を軽く加点
- 回答・判定モデル: Ollama `gemma4:latest`
- seed: 42
- 質問ごとに回答と盲検判定を分離

Oracleは`ground-truth/expected.json`から生成した理想知識であり、実装精度ではない。ActualはOllamaで抽出したFRAGARACHのBuildを使い、決定的な再コンパイルでFront Matter、権威性、重複別名、不足診断、Conflictを更新した。

## 同一実験内の結果

| 指標 | Raw RAG | Oracle | Actual Build |
|---|---:|---:|---:|
| 根拠再現率@5 | 82.3% | 96.9% | 90.6% |
| 引用再現率 | 76.0% | 61.5% | 76.0% |
| 必須回答要素の再現率 | 96.9% | 95.3% | 88.5% |
| Behavior Accuracy | 100.0% | 100.0% | 100.0% |
| 禁止誤答率 | 6.3% | 6.3% | 0.0% |
| 未裏付け引用率 | 0.0% | 0.0% | 0.0% |
| Strict Pass率 | 50.0% | 37.5% | 50.0% |

機械可読結果は`target/benchmarks/final-comparison-v22/upper-bound-report.json`、各回答は同ディレクトリのJSONLへ保存した。

## 反復時の揺れ

最終Actualアダプターを同じtop-k、モデル、seedで3回実行したStrict Pass率は56.3%、50.0%、50.0%で、中央値は50.0%だった。根拠再現率@5は検索が決定的なため3回とも90.6%、Behavior Accuracyは100.0%、禁止誤答率は0.0%だった。

Strict Passの揺れは回答生成とLLM判定に由来する。単発の最高値だけを採用せず、最終判断には同一比較の50.0%と反復中央値50.0%を使う。

## 実装によって改善した点

Source文書単位の抽出バッチと境界Evidenceの重なりにより、異なる文書を一度の抽出へ混ぜず、長い文書の文脈を保った。ClaimはEvidence参照が実在する場合だけ採用し、相対期限を適用日と誤認した候補はRust側で補正する。

Front Matterの`effective_from`、`effective_to`、`status`と、`corpus.yaml`の権威順位・パス規則をEvidenceとClaimへ適用した。検索時にはIntentと`as_of`で絞り、正式標準を補助ガイドより優先する順位を回答コンテキストにも示す。

完全重複は一つのEvidenceへ統合するが、元の全パスを引用別名として保持する。これにより、内容が同じ共有コピーを一次文書として選んでも、期待する原本パスへ遡れる。

同じ節のチェックリストで担当者が一部だけ欠ける場合、関連Intentに限ってMissing Informationを出す。QA-001では担当者を推測せず、出荷判定会議で決める必要を示し、Strict Passになった。

## 残った失敗

Actualの根拠再現率90.6%はRawより高いが100%ではない。別名関係、会議記録と正式標準の組合せ、提案から実装までのイベント列の一部で、必要な二文書の片方しかtop 5へ入らない質問が残った。

正しいEvidenceを取得した設問でも、回答モデルが必要な承認条件を一つ省略したり、競合元の引用をすべて付けなかったりした。これはClaim抽出だけでなく、検索単位の構成、質問ごとの再ランキング、Answer Contractの強制方法に改善余地があることを示す。

Oracleの根拠再現率が最も高いのにStrict Passが低いことからも、構造化知識を作るだけでは不十分である。回答器が必要な根拠集合と時点・権威の解決理由を消費できなければ、上限性能は回答へ伝わらない。

## 精度に関する判断

現状を「通常RAGより成果が出ているか」と問うなら、答えは観点によって分かれる。

- 根拠検索: 改善している。82.3%から90.6%
- 安全性: 改善している。禁止誤答率6.3%から0%
- 引用: 同等。76.0%
- 回答の完全性: 悪化している。96.9%から88.5%
- 総合Strict Pass: 同等。50.0%

このため、FRAGARACHのコンセプトは実データで試す価値があるが、0.1.0を精度向上製品として約束する段階ではない。次の合格条件は、Actualの根拠再現率を維持したまま、回答要素とStrict PassをRaw以上へ安定させることである。

## 次の評価

次は、汎用`export`のJSONLから評価用索引を構築し、評価専用のBuild readerに依存しないことを確認する。そのうえで、質問に応じたClaim/Evidenceの再ランキング、必須引用集合を明示するAnswer Contract adapter、イベント列の検索単位を改善する。

品質評価は、別seedの反復だけでなく、異なる回答モデル、LLMと独立した決定的判定、人手による方式非開示の確認を併用する。実データでは、Intentごとに通常質問、旧版、矛盾、未採用案、不足、回答保留を含む評価セットを作る。
