# Tuned Raw RAG評価

実施日: 2026-08-01

500文書・100問に対して、Fragrachのコンパイル結果を使わない純粋なRaw RAGを調整した。最初に回答LLMを使わず検索条件を選び、その後、選択した条件を既存の回答・判定処理へ接続する。

## 条件選択

質問はIntentと既存／追加群を保ったまま、73問の開発群と27問の保留群へ決定的に分割した。条件選択には開発群だけを使い、R@5、R@10、Conflict complete@10、不要単位率、索引サイズの順で比較した。

一次探索では、次の80条件を比較した。

- 段落、固定長、節単位のチャンク
- 固定長チャンクの段落重なり
- Front Matterを索引へ含めるか
- 日本語1-gram、2-gram、3-gramの組み合わせ
- 質問へ`as_of`を検索語として付けるか

一次探索の上位8条件について、BM25の`k1`を5段階、`b`を4段階で調整した。合計240条件である。

選択された条件は次のとおりである。

| 項目 | 値 |
|---|---|
| Profile | `tuned-sparse-v1` |
| Chunk | 節境界を越えない最大1,024文字 |
| Overlap | 0段落 |
| Front Matter | 含める |
| 検索Token | 日本語文字2-gram |
| Query | 質問本文だけ。`as_of`を機械的に追加しない |
| BM25 | `k1=1.8`、`b=0.75` |
| 索引単位 | 2,461 chunks |

## 検索結果

| 条件 | 質問群 | R@5 | R@10 | R@20 | Conflict complete@10 | 解決精度@10 | 解決Coverage@10 | 不要単位@5 |
|---|---|---:|---:|---:|---:|---:|---:|---:|
| 現行Raw | 全100問 | 57.7% | 72.2% | 92.7% | 84.6% | 90.9% | 84.6% | 77.4% |
| Tuned Raw | 開発73問 | 75.3% | 91.1% | 100.0% | 88.9% | 87.5% | 88.9% | 74.5% |
| Tuned Raw | 保留27問 | 70.4% | 85.2% | 98.1% | 100.0% | 75.0% | 100.0% | 74.1% |
| Tuned Raw | 全100問 | 74.0% | 89.5% | 99.5% | 92.3% | 83.3% | 92.3% | 74.4% |

全100問では、現行Rawに対してR@5が16.3ポイント、R@10が17.3ポイント、R@20が6.8ポイント改善した。保留群でもR@5 70.4%、R@10 85.2%であり、全100問の選択後スコアだけに現れた改善ではない。

矛盾の両側をtop 10へ取得できた質問は84.6%から92.3%へ増えた。一方、両側を取得した場合に正規側を上位へ置けた割合は90.9%から83.3%へ下がった。関連する文書を集める能力と、時点・権威性から正規文書を優先する能力は別であり、Sparse tuningだけでは後者を保証できない。

Intent別では、Compliance AuditはR@5 93.3%、Onboardingは100%まで改善した。Incident ResponseはR@5 54.3%だがR@10 100%であり、必要根拠は存在するもののtop 5の順位に課題がある。Project HistoryはR@5 50.0%、R@10 57.5%にとどまり、複数文書の経緯を短い検索で集めることが難しい。

## 現時点の目標値

Fragrachの検索は、従来のRaw RAG 57.7%ではなく、少なくとも次のTuned Raw Sparseを比較目標とする。

- R@5: 全100問74.0%、保留群70.4%
- R@10: 全100問89.5%、保留群85.2%
- R@20: 全100問99.5%、保留群98.1%
- Conflict complete@10: 全100問92.3%
- 解決精度@10: 全100問83.3%、Coverage 92.3%

これはSparse検索だけの目標である。密検索とrerankを加えたTuned Raw Hybridを次に測り、通常RAGの最終目標を更新する。

## 再現方法

探索を再実行する。

```powershell
npm run benchmark:raw-tune
```

選択済みProfileを検索だけ再測定する。

```powershell
node tests/benchmarks/rag-comparison/run-upper-bound.mjs `
  --corpus tests/corpora/aobane-industries-ja-medium `
  --output target/benchmarks/tuned-raw-recheck `
  --raw-only `
  --raw-profile tuned-sparse-v1 `
  --retrieval-only `
  --retrieval-k 5,10,20
```

機械可読な全探索結果は`target/benchmarks/raw-rag-tuning/raw-tuning-report.json`、選択済みProfileの再測定は`target/benchmarks/tuned-raw-recheck/retrieval-report.json`へ保存される。

## 回答評価

選択したSparse条件を固定し、`gemma4:latest`で100問を回答・盲検判定した。top 5とtop 10の結果は次のとおりである。

| 指標 | Tuned Raw top 5 | Tuned Raw top 10 | 差 |
|---|---:|---:|---:|
| 根拠再現率 | 74.0% | 89.5% | +15.5pt |
| 引用再現率 | 61.0% | 69.3% | +8.3pt |
| 回答要素 | 88.7% | 90.3% | +1.7pt |
| Behavior Accuracy | 93.0% | 93.0% | 0.0pt |
| 禁止誤答率 | 1.0% | 1.0% | 0.0pt |
| 未裏付け引用率 | 0.0% | 0.0% | 0.0pt |
| Strict Pass | 20.0% | 35.0% | +15.0pt |
| 回答入力token合計 | 93,683 | 154,946 | +65.4% |
| 回答出力token合計 | 22,990 | 25,738 | +12.0% |
| 平均回答遅延 | 6.88秒 | 7.66秒 | +11.5% |

top 10ではStrict Passが35.0%となり、top 5より15.0ポイント改善した。とくにIncident Responseは4.3%から82.6%へ改善し、R@10 100%の取得結果を回答へ変換できた。一方、Project Historyは0%から5.0%にとどまり、R@10自体も57.5%である。単純に取得数を増やすだけでは、複数文書にまたがる意思決定履歴を揃えられない。

また、Compliance AuditのStrict Passはtop 5の26.7%からtop 10の10.0%へ低下した。必要根拠が増えた質問でも、競合文書や不要な候補をそのまま回答モデルへ渡すと引用の選択を損なう。入力tokenも65.4%増えた。したがって、純粋なSparse RAGの回答目標はtop 10の全体Strict Pass 35.0%とするが、完成形として固定top 10を採用するのではない。B2では広く候補を取得した後にrerankし、質問に必要な根拠だけをtop 5前後へ絞る。

既存16問と追加84問を分けると、top 10のStrict Passはそれぞれ50.0%と32.1%である。追加群でも検索根拠再現率90.2%、引用再現率69.8%を得ており、既存16問だけに合わせた結果ではない。ただし既存群では1問の禁止誤答が残り、禁止誤答率0%は未達である。

以上から、Fragrachが次に超えるべき暫定目標を次の二つに分ける。

- 検索目標: R@5 74.0%、R@10 89.5%、Conflict complete@10 92.3%、解決精度@10 83.3%
- 回答目標: Strict Pass 35.0%、引用再現率69.3%、回答要素90.3%、禁止誤答率1.0%以下

これらはTuned Raw Sparseの目標である。Hybrid検索とrerankを加えたB2が上回った場合は、その値を純粋RAGの最終目標へ更新する。
